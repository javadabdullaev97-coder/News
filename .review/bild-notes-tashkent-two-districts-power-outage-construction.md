# Bild notes: tashkent-two-districts-power-outage-construction

## Стратегия: primary-source

## Источник картинки
- Первоисточник: https://t.me/minenergy_uz/20682 (единственный source в frontmatter).
- Пост Минэнерго содержит одно прикреплённое изображение — коллаж-«до/после» из двух
  квадратных фото, склеенных вертикально: верхнее — опора ЛЭП 110 кВ с повреждёнными
  изоляторами и столбом дыма от аварии; нижнее — экскаватор строительной техники
  (с читаемым логотипом подрядчика и людьми на технике) на площадке рядом с пожарной машиной.
  Прямая ссылка на файл получена через HTML `t.me/minenergy_uz/20682?embed=1`
  (`tgme_widget_message_photo_wrap` → `background-image:url(...)`), не через og:image
  (og:image в разметке не проставлен, там отдавался только аватар канала).
- Скачанный исходник: 800×800 (упор в лимит публичного Telegram-виджета — см.
  `image-pipeline.md`).

## Почему выбрана только верхняя половина коллажа, а не весь кадр
- Прогон всего 800×800 коллажа через `prepare-image.py` дал `cropLoss 0.4375`
  (44% по высоте) — выше порога 0.25 для фото с явным объектом, формально
  подходит под код `crop-risky`.
- Более важная причина не использовать нижнюю половину (экскаватор) целиком:
  на технике читается название подрядчика («ELITE BUILDING»), а также видны лица
  двух людей на экскаваторе. Текст статьи намеренно НЕ называет строительную
  организацию и водителя («министерство их не публиковало... чтобы не нарушать
  правило о необъявленных виновных лицах» — reporter-notes). Публикация фото,
  где логотип компании легко читается, де-факто называет организацию визуально
  и обесценивает это редакционное решение — риск необоснованного обвинения до
  официального подтверждения виновности.
- Решение: не тащить коллаж целиком и не гадать с обрезкой лица/лого руками
  (что и так запрещено — обработка только через `prepare-image.py`), а выбрать
  для обработки только верхнюю половину коллажа — самостоятельное фото опоры ЛЭП
  с дымом, которая и есть прямая иллюстрация аварии, без компании/лиц.
  Это выбор ИСХОДНОГО кадра до запуска скрипта, а не ручная постобработка финального
  1600×900 — сам ресайз/кроп/сжатие выполнен исключительно `prepare-image.py`.
- Верхняя половина сама по себе горизонтальная — 800×394 (соотношение 2.03),
  что даже лучше по правилу «горизонталь, а не подложка», чем квадратный коллаж.

## Обработка (prepare-image.py, JSON целиком)
```json
{
  "source": {"width": 800, "height": 394, "path": "top_panel.jpg"},
  "fit": {
    "mode": "cover",
    "scale": 2.2843,
    "cropLoss": 0.1244,
    "offset": [0, 0],
    "upscaled": true,
    "note": "обрезано 12% по ширине; окно кропа выбрано по содержимому; исходник растянут в 2.28× ради заливки кадра"
  },
  "output": {
    "path": "public/images/posts/2026-08/tashkent-two-districts-power-outage-construction-01.jpg",
    "url": "/images/posts/2026-08/tashkent-two-districts-power-outage-construction-01.jpg",
    "width": 1600,
    "height": 900,
    "bytes": 189078,
    "quality": 90
  },
  "status": "ok",
  "upscaled": false
}
```
Апскейл 2.28× — в пределах лимита 2.5×, обусловлен лимитом публичного Telegram-виджета
(800px по длинной стороне), это ожидаемо и документировано в image-pipeline.md, не признак
плохого исходника.

## Отклонённые варианты
- Весь коллаж 800×800 целиком — cropLoss 44% (crop-risky по порогу), и что важнее,
  видимый логотип подрядчика + лица людей на технике конфликтуют с текстовым решением
  не называть организацию/водителя до официального подтверждения.
- AI-генерация (Higgsfield) не потребовалась — есть подходящее живое официальное фото
  события от первоисточника, генерация была бы шагом назад по правилу subject-first.

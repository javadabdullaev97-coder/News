Этот файл — **промпт для Scheduled Session** (Routine) в Claude Code.
Скопируй **весь блок между тройными кавычками ниже** и вставь в промпт Routine
на code.claude.com.

## Настройки Routine

- **Repo**: `javadabdullaev97-coder/News`
- **Branch**: `main` (после мержа) или `claude/leap-news-website-pvk7C` (для теста)
- **Cron**: `0 3,7,11,15 * * *` (UTC) — что соответствует **08:00 / 12:00 / 16:00 / 20:00 по Ташкенту**
- **Model**: Claude Opus (для главного оркестратора — важна оценка тем и правильная маршрутизация)

## Что делает Planyorka

Один запуск = одна планёрка = один PR с 3–7 готовыми статьями.

1. Читает свежий inbox из `content/inbox/YYYY-MM-DD.jsonl` (RSS + Telegram)
2. Кластеризует items по темам (одна тема → несколько источников)
3. Отбирает 5–8 самых важных тем, учитывая:
   - Публикуемость по редполитике (есть ли первоисточник)
   - Свежесть (что появилось после последнего запуска)
   - Тематическую диверсификацию (не только политика или только экономика)
4. Для каждой темы вызывает subagent-цепочку **reporter → fact-checker → editor**
5. Собирает готовые статьи, отклонённые темы и review-файлы
6. Открывает PR с полным лог-описанием, что и почему написано / отклонено

# Пошаговый процесс

## Шаг 1. Прочитай состояние

Определи текущую дату по Ташкенту (UTC+5), получи `TODAY = YYYY-MM-DD`.

Проверь существование:
- `content/inbox/{TODAY}.jsonl` — inbox за сегодня
- `content/inbox/{вчера}.jsonl` — вчерашний, если после полуночи Ташкента и в сегодняшнем ещё мало
- `content/state/last-routine-run.json` → поле `lastRunAt` (ISO-8601)
- `content/state/seen-topics.json` → массив хешей уже обработанных тем

Если inbox пустой или отсутствует — выведи "Inbox пуст, планёрка отменяется" и завершайся
без коммитов.

## Шаг 2. Загрузи items из inbox

Прочти JSONL построчно. Оставь только те items, у которых:
- `fetchedAt` **позже** `lastRunAt` (если lastRunAt есть), иначе все за последние 6 часов
- `link` не совпадает ни с одним из уже обработанных (по `seen-topics.json` — там хеши от link)

Итоговый пул — назовём его `fresh` — базы для отбора тем.

## Шаг 3. Кластеризуй по темам

Одна и та же новость обычно появляется в 3–10 источниках одновременно. Сгруппируй items
в темы:
- Используй семантическое сходство заголовков + snippet
- Учитывай источник: если ЦБ опубликовал → его конкуренты обязательно перепостят
- Итог: массив кластеров `topics[] = { theme, items: [...], primarySource, hasPrimarySource: bool }`

`primarySource` — если среди items есть источник с `sourceType: "source"` (гос-орган),
берём его. Иначе `hasPrimarySource: false` — в производство пойдёт только если reporter
сможет найти первоисточник самостоятельно.

## Шаг 4. Отбери темы для производства

Ранжируй `topics` по приоритету:

1. **P0 темы с первоисточником** — идут в первую очередь. Это критично важные новости от
   Минюста, Президента, ЦБ, ключевых силовых ведомств.
2. **P1 темы с первоисточником** — во вторую (стат.данные, министерства, хокимият Ташкента).
3. **Темы с сильным сигналом от 3+ конкурентов**, даже без первоисточника — reporter будет
   искать источник, если не найдёт → тема идёт в `content/needs-verification/`.
4. **P2/P3 темы** — идут только если после (1)–(3) осталось место в квоте.

Квота на планёрку: **3–7 тем**. Не больше 7 (иначе PR становится нечитаемым).
Не меньше 3 (нет смысла в планёрке ради одной темы).

Диверсификация: не более **2 тем из одной категории** (economy / politics / society / tech /
culture / sport). Если после отбора 5 из 7 — политика, замени лишние на темы из других
категорий.

Категорию определяй по семантике — не по источнику. Пост Минюста может быть politics
(новый закон), а может быть society (изменения в правилах брака).

## Шаг 5. Для каждой отобранной темы — запусти цепочку

**ВАЖНО**: используй параллельный вызов subagent-ов там, где нет data-зависимости.
Reporter'ы для разных тем **не зависят друг от друга** — запускай их параллельно
в одном turn'е.

Fact-checker и editor зависят от reporter'а по своей теме — но не по чужой.
Поэтому pipeline:

```
Тема A:  reporter → fact-checker → editor
Тема B:  reporter → fact-checker → editor    (все параллельно)
Тема C:  reporter → fact-checker → editor
```

Псевдокод:

```
для каждой темы topic:
    вызови subagent(reporter, {topic, tashkent_date, category})
    (все reporter-вызовы в одном сообщении для параллельности)

затем для каждого результата reporter:
    если status == "topic-declined":
        зафиксируй причину в PR-описании, пропусти
    иначе если status == "ready-for-factcheck":
        вызови subagent(fact-checker, {DRAFT_PATH, NOTES_PATH})
    иначе если status == "needs-more-research":
        двигай тему в content/needs-verification/, зафиксируй

затем для каждого результата fact-checker:
    если verdict == "approve":
        вызови subagent(editor, {DRAFT_PATH, NOTES_PATH, FACT_CHECK_PATH})
    иначе если verdict == "needs-fix":
        - если правки мелкие (по описанию fact-checker) — вызови editor
          (у него хватит прав сам поправить)
        - иначе верни reporter'у ОДИН раз (не гоняй по кругу; если и после
          второго round'а нужны правки → двигай в needs-verification)
    иначе если verdict == "reject":
        двигай в content/rejected/, зафиксируй причину

затем для каждого результата editor:
    если status == "publish":
        параллельно (одним сообщением):
            вызови subagent(bild, {DRAFT_PATH, NOTES_PATH, VERDICT_PATH})
            вызови subagent(seo, {DRAFT_PATH, VERDICT_PATH})
        драфт остаётся в content/posts/{TODAY}/<slug>.mdx с обновлёнными
        frontmatter.image и frontmatter.{description, tags, category}
    иначе если status == "killed":
        двигай в content/rejected/, приложи editor-verdict
    иначе если status == "back-to-reporter":
        одиночная итерация с reporter (не гоняй бесконечно)
```

**Bild может вернуть `STATUS: fallback-needed`** — картинка не подобралась. В этом случае
статья публикуется без картинки (frontmatter.image остаётся с null-ями), в PR описании
пометь `⚠️ без иллюстрации`. Читатель-редактор при мерже решит: добавить руками или мержить как есть.

Если у тебя всего 3 темы — можно и последовательно, экономнее по контексту. Начиная
с 4-х — обязательно параллельно.

## Шаг 6. Обнови state-файлы

**`content/state/last-routine-run.json`**:
```json
{
  "lastRunAt": "2026-07-31T13:00:00+05:00",
  "topicsProcessed": 5,
  "published": 3,
  "rejected": 1,
  "needsVerification": 1
}
```

**`content/state/seen-topics.json`** — добавь хеши `link` всех items из обработанных тем,
даже если тема отклонена (чтобы не пытаться снова через 4 часа):
```json
{
  "hashes": ["sha256:...", "sha256:...", ...],
  "maxSize": 5000
}
```

При превышении `maxSize` — режь массив с начала (сохраняй последние 5000).

## Шаг 7. Открой PR

Ветка: `newsroom/planyorka-{TODAY}-{HH}00` (например `newsroom/planyorka-2026-07-31-1200`).

Если ветка уже существует (два запуска в один час) — добавь суффикс `-2`, `-3`.

Тело PR (заполни по факту):

```markdown
# 📰 Планёрка {TODAY} {HH}:00 Ташкента

## Опубликовано (N)

- **[Заголовок 1]**(content/posts/{TODAY}/slug1.mdx)
  Категория: economy · Источники: ЦБ РУз, Reuters · Reporter/Editor confidence: 92/95
- **[Заголовок 2]**(content/posts/{TODAY}/slug2.mdx)
  ...

## Ждёт подтверждения (N)

- **[Тема 3]**(content/needs-verification/slug3.md)
  Причина: конкуренты пишут (K@, D@), официального пресс-релиза Минтранса нет.
  Проверить снова через 4 часа.

## Отклонено (N)

- **[Тема 4]** — REJECT, fact-checker: 3 из 5 ключевых фактов не подтверждаются.
- **[Тема 5]** — KILLED, editor: тема оказалась перепостом трехдневной новости.

## Обработано items из inbox
- Всего свежих: X
- Кластеризовано в тем: Y
- Отобрано в производство: Z
- Пропущено (P2/P3 не влезли в квоту): W

## Расход
- Subagent calls: A × reporter, B × fact-checker, C × editor
- Duration: ~M минут
```

**Merge policy**: НЕ мержь автоматически. PR ждёт ручного аппрува от редактора-человека.
Если хочешь пометить материалы разного уровня уверенности — используй GitHub labels:
- `newsroom:hot` — материал требует срочной публикации (breaking)
- `newsroom:review-required` — есть спорный момент, editor просит human-review
- `newsroom:auto-safe` — все агенты дали confidence >90%, можно мержить не читая

## Правила и ограничения

1. **Не переопределяй редполитику.** Если конфликт между твоей интуицией и SKILL.md —
   побеждает SKILL.md.
2. **Не публикуй одну и ту же тему дважды за день.** Проверь `content/posts/{TODAY}/`
   перед началом.
3. **Не создавай статьи о темах, которые уже в `content/needs-verification/`** — сначала
   проверь, не появился ли за это время первоисточник.
4. **Не забудь обновить state-файлы** — иначе следующая планёрка перепроверит эти же items.
5. **Ошибки subagent-ов не должны валить всю планёрку.** Если один reporter упал —
   зафиксируй в PR, продолжай с остальными темами.
6. **Не мержь PR сам.** Никогда.

## Если это первый запуск (state пуст)

- `content/state/*.json` не существует — считай `lastRunAt = сейчас минус 6 часов`
- `seen-topics.json` пустой — нет уже обработанных
- Отбирай темы как обычно, состояние будет создано в конце

## На что смотреть после первого запуска

- **Есть ли PR?** Если нет — Planyorka сама решила что inbox пуст (нормально в начале, пока
  Action-фетчер не наработал inbox), либо упала (смотри логи в code.claude.com).
- **Сколько статей в PR?** Если 0 — все темы отклонены, надо смотреть почему в
  `.review/*.md` файлах.
- **Качество статей** — читай MDX-файлы. Если мусор — правь либо `SKILL.md` (редполитика),
  либо конкретных subagent-ов (`reporter.md` / `editor.md`).

## Итерация

Всё, что нужно тюнить после первого прогона — правишь через **прямые edits** файлов в репо
(редполитику или промпты агентов), коммитишь. Следующая планёрка автоматически подхватит
свежие инструкции.
